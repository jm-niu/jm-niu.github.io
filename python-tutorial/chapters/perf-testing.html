第二十四章：性能优化与测试工程

难度：进阶 预计学习时间：1-2 周 前置知识：部署、API 设计

应用上线后，"快不快、稳不稳"决定了用户体验与留存。本章把测试与性能两件事讲透：用 pytest 写单元测试保证质量、用性能分析定位瓶颈、用缓存与异步任务提速、用 locust 压测验证承载能力。让"能跑"升级为"跑得快、跑得稳、改得安心"。

pytest 写测试 分析性能瓶颈 缓存 + 异步任务 压测验证承载

pytest 单元测试

测试是工程化的基石：它把"我改了代码会不会弄坏旧功能"变成自动可验证的事。pytest 是 Python 最流行的测试框架，写法简单（用 assert 即可）、发现测试自动、报告友好。

Bash
pip install pytest
# 测试函数以 test_ 开头，文件以 test_ 开头
pytest -v            # 详细模式
pytest -k "discount" # 只跑名字含 discount 的测试
Python
# calc.py
def discount(price, rate):
    if not 0 <= rate <= 1:
        raise ValueError("折扣率需在 0~1")
    return round(price * (1 - rate), 2)

# test_calc.py
from calc import discount

def test_discount_normal():
    assert discount(100, 0.2) == 80.0       # 正常用例

def test_discount_zero():
    assert discount(100, 0) == 100.0        # 边界

def test_discount_invalid():
    import pytest
    with pytest.raises(ValueError):        # 期望抛异常
        discount(100, 1.5)

fixture 与 mock

测试常需要"准备数据/环境"。fixture 提供可复用的测试前置；mock 用来替换外部依赖（数据库、网络），让测试只验证自身逻辑、又快又稳。

Python
import pytest
from unittest.mock import patch
from app import create_app, db, Todo

@pytest.fixture
def client():
    app = create_app()
    app.config["TESTING"] = True
    app.config["SQLALCHEMY_DATABASE_URI"] = "sqlite:///:memory:"  # 内存库，测完即弃
    with app.app_context():
        db.create_all()
    return app.test_client()

def test_create_todo(client):
    resp = client.post("/api/todos", json={"task": "写测试"})
    assert resp.status_code == 201
    assert resp.get_json()["task"] == "写测试"

# mock 外部调用（不真的发网络）
@patch("app.notify.send_email")
def test_register_sends_email(fake_send):
    register_user("alice")
    fake_send.assert_called_once()    # 只验证"调用过"，不发真邮件
前端 JS/TS 类比：测试框架

pytest 对应前端的 Vitest/Jest：assert 对应 expect，fixture 对应 beforeEach，mock 对应 vi.fn()/jest.fn()。思路一致——隔离被测单元、用替身代替依赖、断言行为。

JavaScript
// Vitest 写法（对照 pytest）
import { test, expect, vi } from "vitest";
test("discount", () => {
  expect(discount(100, 0.2)).toBe(80);
});
const fakeSend = vi.fn();

性能分析

优化前先测量，凭直觉优化常找错地方。Python 自带 cProfile 统计每个函数耗时，帮你定位真正瓶颈。

Bash
# 命令行分析某个脚本
python -m cProfile -s tottime app.py

# 输出按总耗时排序，找出最慢的函数
# 也可用 snakeviz 可视化 profile 结果
pip install snakeviz
python -m cProfile -o out.prof app.py && snakeviz out.prof

示意图：性能优化循环 —— 猜测 → 测量 → 定位 → 优化 → 重测，用数据驱动而非直觉。

缓存与异步任务

常见提速手段：把重复计算或数据库查询结果缓存（如 Redis）；把耗时操作（发邮件、生成报表）丢到异步任务后台执行（如 Celery），不阻塞主请求。

Python
# 简易内存缓存（functools.lru_cache）
from functools import lru_cache

@lru_cache(maxsize=128)
def expensive(n):
    # 结果按参数缓存，相同参数不再重算
    return sum(i * i for i in range(n))

# 进阶：Redis 缓存 + Celery 异步任务
# pip install redis celery
from celery import Celery
celery = Celery("tasks", broker="redis://localhost:6379/0")

@celery.task
def send_welcome_email(user_id):
    # 异步执行，不阻塞主请求
    ...

# 视图里触发
@celery.task
def register():
    send_welcome_email.delay(uid)   # .delay 把任务丢后台
    return "注册成功"
提示

缓存要考虑"失效"：数据更新后要清除或更新对应缓存，否则读到旧数据。可设过期时间（TTL）或主动失效。数据库查询的 N+1 问题（循环里查库）也常是性能杀手，用 joinedload 一次取出关联数据。

压力测试

上线前用压测摸清系统承载：每秒能处理多少请求、响应时间分布、瓶颈在哪。locust 用 Python 写测试脚本，模拟大量并发用户。

Bash
pip install locust
Python
# locustfile.py
from locust import HttpUser, task, between

class TodoUser(HttpUser):
    wait_time = between(1, 3)        # 每个用户每次请求间隔 1~3 秒

    @task
    def list_todos(self):
        self.client.get("/api/todos")    # 模拟访问列表接口

# 启动：locust，浏览器打开 http://localhost:8089
# 设置并发用户数与每秒启动数，观察 RPS、响应时间、失败率
项目案例：测试与优化待办 API

综合本章：给待办 API 写测试，再压测找瓶颈，最后加缓存优化：

Bash
# 1. 跑测试套件
pytest -v                          # 全绿才能上线

# 2. 压测基线
locust                            # 发现 GET /api/todos 在 100 并发时 RPS=120

# 3. 分析：列表接口每次都查库
#    优化：给列表接口加 1 秒短缓存
# 4. 重测：RPS 提升到 800，响应时间下降

这就是"测试保质量、压测定基线、优化看数据、再测验证"的完整闭环。

本章核心要点
  • pytest：用 assert 写测试，自动发现 test_ 开头函数与文件。
  • fixture 准备环境，mock 替换外部依赖，测试快而稳。
  • 优化前先测量：cProfile 定位真正瓶颈，别靠猜。
  • 缓存（lru_cache/Redis）减少重复计算，注意失效策略。
  • 异步任务（Celery）把耗时操作丢后台，主请求快速返回。
  • locust 压测验证承载，用 RPS/响应时间/失败率衡量。

练习建议 动手实践

  1. 写测试 — 给前面的 discount 函数补全覆盖正常/边界/异常的测试。
  2. API 测试 — 用 fixture + test_client 测试待办 API 的增删查。
  3. 性能分析 — 用 cProfile 分析一个慢函数，定位最耗时行并优化。
  4. 压测 — 用 locust 压测待办 API，记录基线 RPS，加缓存后对比提升。
