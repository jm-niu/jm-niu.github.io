三、公开面经原题与解析 ​

1. Service Worker 如何拦截请求并实现缓存？ ​

考察点： 浏览器离线能力、缓存策略、更新机制和异常兜底。

Service Worker 运行在页面主线程之外。页面首次注册后，脚本经历 install、activate，并在控制页面后监听 fetch 事件。event.respondWith() 可以决定返回缓存还是网络响应。

常见策略：

  • Cache First：先缓存，未命中再请求网络。适合带内容哈希的 JS、CSS、图片。
  • Network First：先网络，失败后读缓存。适合更新敏感的页面或接口。
  • Stale While Revalidate：立即返回旧缓存，同时后台更新。适合允许短暂陈旧的内容。

高质量答案还应提到：

  • 缓存要带版本号，在 activate 阶段清理旧版本。
  • 不应无差别缓存鉴权接口和个性化数据。
  • Service Worker 只能在安全上下文（HTTPS，开发时 localhost 例外）使用。
  • 发布新脚本后，旧页面可能仍由旧 Worker 控制，需要设计更新提示或安全的 skipWaiting 流程。

参考：MDN - Using Service Workers。

2. Vue 2 和 Vue 3 的响应式有什么区别？ ​

考察点： 不只是会使用 API，还要理解依赖收集和更新触发。

Vue 2 主要通过 Object.defineProperty 为初始化时已有的对象属性定义 getter/setter。读取时收集依赖，写入时通知 watcher。它不能天然拦截新增/删除属性和数组下标写入，因此需要 $set、数组方法改写等补充机制。

Vue 3 对普通对象使用 Proxy，对 ref 使用 getter/setter。Proxy 可以统一拦截读取、写入、删除、in、键遍历等操作，因此对新增属性、删除属性和数组索引更自然。依赖关系可以概括为：

text
target -> key -> effects
1

读取属性时 track(target, key)，修改时 trigger(target, key)。回答时不要简单说“Proxy 一定更快”，更准确的优势是拦截能力完整、可按访问懒代理嵌套对象，代价则包括不支持 IE、代理对象与原对象身份不同等。

参考：Vue - Reactivity in Depth。

3. Vue 2 与 Vue 3 的 diff 有什么变化？key 为什么重要？ ​

考察点： 虚拟 DOM 更新、节点身份和编译期优化。

两代 Vue 都会在同层级比较同类型节点，不会寻找任意最优树编辑路径。Vue 2 典型的双端比较同时检查新旧列表两端；Vue 3 的 keyed children 更新会先同步比较头尾，再处理未知中间段，并用“最长递增子序列”减少可复用节点的 DOM 移动。

Vue 3 还有编译器提供的 patch flag、静态提升和 block tree，只让运行时重点检查动态部分。这往往比单纯讨论某个 diff 循环更关键。

key 表示节点的稳定身份：

  • 没有稳定 key 时，框架更可能按位置复用节点。
  • 使用数组下标作为 key，在插入、删除、排序时会让“身份”随位置变化，可能导致输入框状态、组件局部状态错位。
  • key 应在兄弟节点中唯一、稳定，并来自业务 ID。

4. React 有哪些性能优化方法？ ​

考察点： 当前多个 React 岗位都要求性能实战，回答必须从测量开始。

建议按“定位 → 状态 → 渲染 → 加载 → 验证”回答：

  1. 用 React DevTools Profiler 和 Performance 面板确认慢在网络、JavaScript、渲染还是布局，找到提交时间长或重复渲染的组件。
  2. 缩小状态作用域；不要把高频变化放在过大的 Context 中；服务端状态、表单状态和 UI 状态分开管理。
  3. 在确有重复计算/渲染成本时使用 memo、useMemo、useCallback，同时保持 props 引用稳定。它们是性能工具，不是默认编码仪式。
  4. 长列表使用虚拟化；大计算可切片、延后，必要时放入 Web Worker。
  5. 路由/组件级拆包，优化图片、字体和第三方脚本，避免生成过大的公共 chunk。
  6. 用优化前后的 LCP、INP、包体积、长任务、React commit 时长和业务成功率证明收益。

容易失分的回答是只背 API，却说不出性能基线、火焰图、改动前后数据和回归保护。

5. TypeScript 和 ESLint 的区别，ESLint 能代替 TypeScript 吗？ ​

考察点： 类型系统与代码质量工具的边界。

不能互相替代：

  • TypeScript 编译器检查类型关系，例如参数、返回值、泛型、联合类型收窄，并把 TS 转成 JavaScript。
  • ESLint 基于语法树执行规则，主要检查潜在错误和代码规范，例如未处理的 Promise、Hooks 规则、危险写法。
  • 配合类型信息的 typescript-eslint 可以做更强的 lint，但底层仍会读取 TypeScript 的类型服务，不等于 ESLint 自己替代类型检查。

在大型中后台中，应把公共模型、接口边界和状态建模好，减少 any 与无依据的类型断言；运行时的外部数据仍需验证，因为 TypeScript 类型在运行时会被擦除。

6. sessionStorage、localStorage 有什么区别？iframe 能共享吗？ ​

考察点： 存储的生命周期、作用域和同源策略。

项目localStoragesessionStorage
作用域同源同源 + 当前顶层浏览上下文（标签页）
生命周期主动清理前一直存在标签页/窗口会话结束时清理
新标签页同源页面可读到同一份数据通常是新的页面会话
API同步同步

iframe 不能只回答“能”或“不能”：同源 iframe 处于同一顶层浏览上下文时可访问对应的 session storage；跨源 iframe 属于另一个 origin，不能直接读父页面的存储，应通过受控的 postMessage 通信。浏览器隐私策略还可能进一步限制第三方存储。

两者都是同步 API，大量读写会阻塞主线程，也不应存储敏感凭据。大数据或结构化查询更适合 IndexedDB。

参考：MDN - sessionStorage。

7. nextTick、Promise、async/await、setTimeout 的执行关系是什么？ ​

考察点： 事件循环、微任务和框架更新队列。

浏览器每轮事件循环大体执行一个 task，然后清空 microtask queue，再给浏览器渲染机会：

  • Promise.then 和 await 后续代码进入微任务队列。
  • setTimeout 回调进入后续任务队列，即使延时写 0 也不会插到当前同步代码中间。
  • Vue 的 nextTick 表示“等待当前批次响应式 DOM 更新完成”，通常借助微任务调度，但它的语义是框架更新边界，不能简单当作一个普通 Promise 排序题。

答题时应先写出具体代码，再按“同步代码 → 已入队微任务（按入队先后）→ DOM 更新/渲染机会 → 后续 task”推演，不能脱离代码给出固定口诀。

8. Vue Router 的 hash 和 history 模式如何实现？ ​

考察点： 浏览器历史 API、路由监听和服务端配合。

  • Hash 模式把路由放在 # 后，监听 hashchange。片段不会作为普通路径发送给服务器，因此静态服务器也较容易直接部署，但 URL 不够自然。
  • History 模式使用 history.pushState / replaceState 改变 URL，并监听 popstate 处理前进后退。刷新 /orders/123 时服务器会收到该路径，所以必须把未知前端路由回退到 index.html，同时排除真实静态资源和后端 API。

两种模式的核心都是：读取当前地址 → 匹配路由记录 → 渲染对应组件。工程回答还应覆盖路由懒加载、鉴权守卫、404 和部署 base path。

9. 从输入 URL 到页面显示发生了什么？ ​

考察点： 网络、浏览器渲染和性能优化的完整链路。

可以按以下顺序回答，再根据面试官追问展开：

  1. 解析 URL，检查 HSTS、Service Worker、HTTP 缓存等。
  2. DNS 查询得到 IP；建立 TCP，HTTPS 还要完成 TLS 握手与证书校验。HTTP/3 则基于 QUIC。
  3. 经过 CDN、负载均衡或网关到达服务，服务器返回状态码、响应头和 HTML。
  4. 浏览器流式解析 HTML 构建 DOM，解析 CSS 构建 CSSOM；普通同步脚本可能阻塞 HTML 解析，defer 与 async 的执行时机不同。
  5. 生成渲染树，执行布局、绘制和合成；图片、字体、脚本继续加载，可能引起重排或布局偏移。
  6. SPA/SSR 应用还可能执行 hydration、接口请求、路由初始化和埋点。

高质量答案会把优化措施放回对应阶段，例如 DNS/CDN、压缩与缓存、关键 CSS、代码拆分、图片尺寸、减少长任务，而不是最后堆一串无上下文术语。

10. HTTPS 为什么更安全？XSS 和 CSRF 如何防护？ ​

考察点： 传输安全不等于应用安全。

HTTPS 通过 TLS 提供：

  • 身份认证：证书链帮助客户端确认服务器身份。
  • 机密性：握手协商出的会话密钥加密传输内容。
  • 完整性：AEAD 等机制能发现数据被篡改。

XSS 是不可信内容被当作脚本执行。防护重点是按上下文输出编码、使用安全模板、避免危险 HTML 注入、必要时做 HTML 白名单净化，并用 CSP 降低漏网攻击的影响。

CSRF 利用浏览器自动携带凭据，让用户在不知情时发起有副作用的请求。防护包括 SameSite Cookie、CSRF Token、校验 Origin/Referer，以及不使用 GET 执行写操作。

HttpOnly 可以降低 Cookie 被脚本直接读取的风险，但不能阻止 XSS 以当前用户身份调用接口；HTTPS 也不会自动消除 XSS/CSRF。

11. 图片很多的页面如何优化？ ​

考察点： 电商 C 端和商家图像处理岗位的核心场景。

应先分析图片是否是 LCP 元素、总传输量、解码耗时、内存和滚动流畅度，再组合方案：

  • 使用 AVIF/WebP 等合适格式，按视觉质量压缩。
  • 通过 srcset / sizes 和图片 CDN 返回与设备、容器匹配的尺寸，避免下载超大原图。
  • 首屏关键图提高优先级，非首屏用 loading="lazy"；不要懒加载 LCP 图片。
  • 写明 width / height 或 aspect-ratio 预留空间，减少 CLS。
  • 大量缩略图控制并发与预加载范围；Canvas/WebGL 场景及时释放对象 URL、纹理和不再使用的位图。
  • 监控真实用户的 LCP、流量、失败率和低端设备内存，而不是只看本机 Lighthouse。

12. 算法：最小覆盖子串（LeetCode 76） ​

题目： 给定字符串 s、t，找到 s 中包含 t 所有字符（含重复次数）的最短子串。

思路： 滑动窗口。右指针扩张直到窗口满足条件，再移动左指针缩小；用 missing 记录还缺多少个字符，可以避免每次扫描整张频次表。

js
function minWindow(s, t) {
  if (t.length === 0 || s.length < t.length) return ''

  const need = new Map()
  for (const char of t) {
    need.set(char, (need.get(char) ?? 0) + 1)
  }

  let missing = t.length
  let left = 0
  let bestStart = 0
  let bestLength = Infinity

  for (let right = 0; right < s.length; right++) {
    const rightChar = s[right]
    const rightNeed = need.get(rightChar) ?? 0

    if (rightNeed > 0) missing--
    need.set(rightChar, rightNeed - 1)

    while (missing === 0) {
      const windowLength = right - left + 1
      if (windowLength < bestLength) {
        bestStart = left
        bestLength = windowLength
      }

      const leftChar = s[left]
      const nextNeed = (need.get(leftChar) ?? 0) + 1
      need.set(leftChar, nextNeed)
      left++

      if (nextNeed > 0) missing++
    }
  }

  return bestLength === Infinity
    ? ''
    : s.slice(bestStart, bestStart + bestLength)
}

四、2026 JD 高概率题与解析 ​

本节是根据当前岗位要求推导的准备题，不是公开面经已经证实的 SHEIN 原题。

13. 大型中后台如何选择 Redux、Recoil 或 Context？ ​

先按状态性质拆分，而不是先选库：

  • 组件内部临时状态留在组件内。
  • URL 可表达的筛选、分页尽量放入路由查询参数。
  • 服务端数据交给带缓存、失效和请求去重能力的数据层。
  • 真正跨页面、跨模块的客户端状态才进入全局状态库。

Redux 的优势是单向数据流、可预测更新、成熟调试和中间件生态，适合复杂业务流程与严格治理；Recoil/原子化方案能让组件订阅更细，适合依赖图明显的派生状态；Context 更适合主题、语言、当前用户等低频全局依赖，不宜承载高频且庞大的业务状态，否则 Provider value 变化可能扩大重渲染范围。

面试时应结合团队规模、调试需求、持久化、异步流、性能和迁移成本，而不是回答“哪个更新”。

14. 微前端如何做脚本、样式和依赖隔离？ ​

先判断是否真的需要微前端：它主要解决多个团队独立开发、发布和演进，不是为了把一个正常 SPA 变复杂。

常见隔离方式：

  • JavaScript：Proxy 沙箱记录/代理全局变量，应用卸载时恢复；更强隔离可用 iframe，但通信、路由、样式融合和体验成本更高。
  • CSS：命名空间、CSS Modules、构建时选择器前缀、Shadow DOM。运行时简单加前缀不能解决所有弹层、动画名和第三方样式问题。
  • 依赖：externals、import map 或 Module Federation 共享 React 等依赖，但必须约束版本兼容和单例要求。
  • 通信：优先稳定、显式的事件或共享契约，避免子应用直接修改主应用内部状态。

治理还应覆盖路由冲突、公共能力版本、灰度、监控上下文、故障隔离、独立回滚和本地联调。

15. Webpack 和 Vite 的核心差异是什么？如何优化构建？ ​

开发阶段，Webpack 通常先构建依赖图并产出 bundle，再由 dev server 提供；Vite 利用浏览器原生 ESM 按需转换业务模块，并用 esbuild 预构建依赖，因此冷启动通常更快。生产阶段 Vite 默认仍通过 Rollup 打包，所以不能把它概括为“Vite 永远不打包”。

优化前要先测量：

  • 开发冷启动、热更新耗时。
  • 生产构建各阶段耗时和模块数量。
  • chunk 体积、重复依赖和缓存命中率。

可用措施包括持久化缓存、缩小 loader/plugin 处理范围、并行化、合理拆包、依赖去重、按需引入和 Monorepo 增量任务。Tree Shaking 依赖可静态分析的 ESM、正确的副作用声明和压缩阶段，CommonJS 的动态特性会限制静态分析。

参考：Vite - Why Vite 和 Webpack - Tree Shaking。

16. Canvas、SVG、DOM 和 WebGL 如何选？ ​

技术适合场景主要限制
DOM/CSS表单、文本、可访问交互、普通动效海量节点布局/绘制成本高
SVG中小规模矢量图、图表、需要节点事件的图形图元很多时 DOM 数量膨胀
Canvas 2D图片处理、画板、海量 2D 图元位图画布没有天然节点树，命中检测和可访问性需自建
WebGL3D、大量粒子、GPU 并行渲染工程复杂，资源生命周期和兼容降级要求高

WebGL/3D 优化可从减少 draw call、合批/实例化、降低 overdraw、压缩纹理和模型、LOD、视锥剔除、按需渲染、Worker 解析资源等方向展开。排查时同时观察 CPU 主线程、GPU、显存、网络资源和帧时间。

17. WebAssembly 什么时候值得用？ ​

适合计算密集、算法边界清晰、已有 Rust/C/C++ 库可复用的模块，例如图片编解码、压缩、几何计算和音视频处理。它不是“把普通业务 JS 换掉就一定更快”。

关键成本：

  • JS 与 Wasm 频繁跨边界调用有开销，应尽量批量传递。
  • 字符串、对象不能无成本共享，通常要通过线性内存和 TypedArray 编解码。
  • 下载、编译、初始化也有成本，需要评估缓存、流式实例化和降级路径。
  • DOM 操作仍主要由 JavaScript 完成。

面试最好给出基准测试方案：定义真实输入规模，同时比较总耗时、初始化、内存、主线程阻塞和低端设备表现。

18. 如何建立可量化的前端性能优化闭环？ ​

一个完整回答应包含：

  1. 目标：例如结算页移动端 P75 LCP、INP、错误率和转化率。
  2. 采集：真实用户监控区分地区、网络、设备、版本和页面；实验室数据用于复现。
  3. 定位：资源瀑布、Long Task、Performance trace、React/Vue profiler、接口链路。
  4. 治理：性能预算、构建产物检查、灰度和告警。
  5. 验证：对比同口径分位数，并观察业务指标和异常回归。

截至本文更新时，Core Web Vitals 重点关注 LCP、INP 和 CLS。只报平均值容易掩盖长尾，跨境电商还要特别关注弱网、远距离网络和低端设备。

参考：web.dev - Web Vitals。

19. Next.js 的 SSR、CSR 与 hydration 分别解决什么问题？ ​

  • CSR：浏览器下载 JavaScript 后获取数据并渲染，交互灵活，但首屏可能依赖较多脚本和请求。
  • SSR：服务器为请求生成 HTML，可改善首屏内容到达和 SEO，但会增加服务端计算、缓存与数据一致性复杂度。
  • hydration：客户端 React 在已有服务端 HTML 上绑定事件并建立组件状态。服务端和客户端首次输出不一致会产生 hydration mismatch。

选择应以页面特征为准：公开商品/营销内容适合服务端生成或静态化；登录后高度个性化且交互密集的后台不必为了“用了 SSR”而 SSR。还要说明缓存键、用户态隔离、流式渲染、错误边界和第三方浏览器 API 的客户端边界。

20. 如何安全地把 AI Coding 接入团队研发流程？ ​

当前两个岗位明确提到 AI Coding/AI Code Review。好的回答不能只说“用 Cursor 提效”，而应给出治理闭环：

  • 明确哪些仓库、数据和代码可以发给外部模型，敏感信息先脱敏或使用获批环境。
  • AI 产出必须经过人审、类型检查、针对改动文件的 lint/测试和安全扫描，责任仍由提交者承担。
  • 警惕幻觉 API、过度抽象、依赖投毒、许可证和生成代码重复问题。
  • 用 PR 周期、返工率、缺陷率、测试覆盖变化衡量收益，不能只统计生成代码行数。
  • Code Review 让 AI 做重复检查和风险提示，人负责业务语义、架构和最终判断。

21. 如何讲好“项目中最有挑战的问题”？ ​

用 STAR 结构，但技术面要多讲决策证据：

  • Situation：业务规模、用户、设备、流量和原有限制。
  • Task：你的责任和可量化目标。
  • Action：如何定位，比较过哪些方案，为什么选择当前方案，如何灰度和兜底。
  • Result：同口径数据、业务收益、线上稳定性和后续沉淀。

面试官继续追问“还有更好的方案吗”时，可以说明当时受交付时间、兼容性、团队能力或迁移成本限制的取舍，以及如果重做会如何演进。不要把团队成果全说成个人完成，也不要只描述“很难、加班解决了”。
